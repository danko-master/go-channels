## Структура канала

`hchan - в исходном коде Go она находится в файле src/runtime/chan.go`

```
type hchan struct {
	qcount   uint           // Всего элементов в буфере. Для небуферизованного ВСЕГДА = 0
	dataqsiz uint           // Размер буфера. Для небуферизованного ВСЕГДА = 0
	buf      unsafe.Pointer // Указатель на массив элементов буфера. Тут он равен nil
	elemsize uint16         // Размер одного элемента в байтах (например, 8 для int64)
	closed   uint32         // Флаг закрытия канала (0 — открыт, 1 — закрыт)
	elemtype *_type        // Информация о типе данных (нужно для работы GC)
	sendx    uint           // Индекс записи в буфер. Не используется (всегда 0)
	recvx    uint           // Индекс чтения из буфера. Не используется (всегда 0)

	// ОЧЕРЕДИ ОЖИДАНИЯ — Самая важная часть небуферизованного канала
	recvq    waitq          // Список ЗАБЛОКИРОВАННЫХ горутин, которые ждут ЧТЕНИЯ
	sendq    waitq          // Список ЗАБЛОКИРОВАННЫХ горутин, которые ждут ЗАПИСИ

	lock     mutex          // Мьютекс для защиты всех полей структуры при обращении из разных потоков
}
```

## Небуферизованный канал

Вся логика работы небуферизованного канала держится на трех полях: recvq, sendq и lock

1. Очереди ожидания (waitq).
   Поскольку буфера для данных нет (buf = nil), каналу нужно где-то фиксировать горутины, которые пришли и заблокировались. Для этого используются две очереди waitq, реализованные как двусвязные списки из структур sudog.sudog — это системная обертка рантайма над горутиной G. Она хранит указатель на саму горутину, указатель на переменную, куда нужно записать/считать данные, и ссылки на следующий/предыдущий элементы списка.

2. Внутренний мьютекс (lock).
   Несмотря на то, что каналы используются для безопасного обмена данными без явных мьютексов со стороны программиста, внутри самого канала мьютекс есть всегда. Когда горутина пытается прочитать или записать в канал, она на доли микросекунды блокирует структуру hchan, чтобы проверить очереди, изменить счетчики или добавить себя в список ожидания.

```
ch := make(chan int)
```

```
          Структура hchan в памяти
+------------------------------------------+

| qcount: 0                                |  <- пустой
| dataqsiz: 0                              |  <- без буфера
| buf: nil                                 |  <- указывает в никуда
+------------------------------------------+

| lock: [Низкоуровневый мьютекс ОС]        |  <- защищает канал
+------------------------------------------+

| recvq (Очередь читателей):               |
|   [sudog (G1)] <-> [sudog (G2)] <-> nil  |  <- Горутины, застрявшие на `<-ch`
+------------------------------------------+

| sendq (Очередь писателей):               |
|   nil                                    |  <- Писателей сейчас нет
+------------------------------------------+
```

Если горутина G1 пришла читать из пустого канала, она создает структуру sudog, кладет туда указатель на свою переменную для результата, прикрепляет этот sudog к списку recvq и засыпает.
Когда приходит горутина G2 с операцией записи ch <- 42, она захватывает lock канала.
Видит, что в буфере ничего нет (dataqsiz == 0), но в очереди recvq есть живой читатель (G1).
Извлекает sudog горутины G1 из очереди.
Напрямую копирует число 42 из своего стека в стек горутины G1 (по адресу, указанному в sudog).
Меняет статус G1 на «готова к выполнению» (\_Grunnable) и отправляет её в планировщик GMP.
Отпускает lock.
Благодаря очередям recvq и sendq рантайм Go точно знает, кого нужно разбудить и куда положить данные в момент «рандеву».

## Буферизованный канал

При создании канала через make(chan T, capacity) рантайм Go выделяет в памяти реальный массив (кольцевой буфер) для хранения элементов и инициализирует счетчики.

```
type hchan struct {
	qcount   uint           // Текущее кол-во элементов в буфере (например, 2)
	dataqsiz uint           // Максимальная емкость буфера. Тут она равна 3
	buf      unsafe.Pointer // УКАЗАТЕЛЬ НА МАССИВ в памяти из 3-х элементов [int, int, int]
	elemsize uint16         // Размер одного элемента (для int на 64-бит ОС это 8 байт)
	closed   uint32         // Флаг закрытия канала (0 — открыт, 1 — закрыт)
	elemtype *_type        // Информация о типе данных для сборщика мусора (GC)

	// ИНДЕКСЫ ДЛЯ КОЛЬЦЕВОГО БУФЕРА
	sendx    uint           // Индекс: куда будет записан СЛЕДУЮЩИЙ элемент (от 0 до 2)
	recvx    uint           // Индекс: откуда будет прочитан СЛЕДУЮЩИЙ элемент (от 0 до 2)

	// ОЧЕРЕДИ ОЖИДАНИЯ — задействуются, только когда буфер пуст или переполнен
	recvq    waitq          // Список горутин (sudog), застрявших на чтении, когда буфер был ПУСТ
	sendq    waitq          // Список горутин (sudog), застрявших на записи, когда буфер был ПОЛЕН

	lock     mutex          // Мьютекс для защиты полей от гонки данных при обращении из разных потоков M
}
```

Буфер реализован как циклический массив (круговая очередь).
Это сделано для того, чтобы не двигать элементы в памяти влево при каждом чтении (что было бы очень медленно).
Индексы sendx и recvx просто ходят по кругу.
Пример работы по шагам.

1. Инициализация: ch := make(chan int, 3).
   Буфер пуст.
   qcount = 0,
   sendx = 0,
   recvx = 0.
2. Первая запись ch <- 10: Рантайм захватывает lock, кладет 10 в buf[0].
   Увеличивает sendx до 1.
   qcount становится 1.
3. Вторая запись ch <- 20: Данные кладутся в buf[1].
   sendx становится 2.
   qcount становится 2.
4. Первое чтение <-ch: Рантайм берет данные из buf[0] (это число 10).
   Увеличивает recvx до 1.
   qcount уменьшается до 1.
5. Третья запись ch <- 30: Данные кладутся в buf[2].
   sendx сбрасывается в 0 (вернулся в начало круга).
   qcount равен 2.

Представим ситуацию, когда в канале make(chan int, 3) уже лежат два элемента, а свободным остался только один слот:

```
                  Структура hchan в памяти
+-------------------------------------------------------------+

| qcount: 2  | dataqsiz: 3 | sendx: 2 (в конец) | recvx: 0    |
+-------------------------------------------------------------+

| buf:  [  10  ]  ,  [  20  ]  ,  [  empty  ]                 |
|          ^                         ^                        |
|   отсюда будем читать       сюда будем писать               |
+-------------------------------------------------------------+

| lock: [Низкоуровневый мьютекс ОС]                           |
+-------------------------------------------------------------+

| recvq (Очередь читателей):  nil                             | <- Никто не спит,
+-------------------------------------------------------------+    в буфере есть данные

| sendq (Очередь писателей):  nil                             | <- Никто не спит,
+-------------------------------------------------------------+    в буфере есть место

```

Очереди ожидания recvq и sendq у буферизованного канала вступают в игру только тогда, когда буфер перестает справляться с потоком данных.

- Буфер переполнен (qcount == dataqsiz):
  Если горутина G_writer пытается сделать запись ch <- 40, а свободного места нет, она не может положить данные в buf.
  Рантайм создает обертку sudog для этой горутины, прикрепляет её к очереди sendq и усыпляет горутину. Как только кто-то сделает чтение <-ch, освободив одну ячейку в массиве, рантайм достанет G_writer из sendq, перенесет её данные в буфер и разбудит.

- Буфер пуст (qcount == 0):
  Если горутина G_reader пытается прочитать данные, а массив пуст, она блокируется.
  Рантайм упаковывает её в sudog, кладет в очередь recvq и отправляет спать. Как только появится писатель, рантайм (в целях оптимизации) скопирует данные напрямую из стека писателя в стек этой спящей горутины, даже не задействуя массив buf (механизм Direct Copy), после чего разбудит её.

# nil канал

Память под структуру hchan еще не выделена

```
var ch chan int
```

Главная особенность nil канала заключается в том, что операции с ним не вызывают панику (panic) приложения (в отличие от вызова методов у nil указателей или записи в nil мапу), но приводят к вечной блокировке.  
Используется для "отключения" ветки в select.

```
func main() {
	ch1 := make(chan int)
	ch2 := make(chan int)

	// Фоновые отправители для примера
	go func() { ch1 <- 10; close(ch1) }()
	go func() { ch2 <- 20; close(ch2) }()

	for ch1 != nil || ch2 != nil {
		select {
		case v, ok := <-ch1:
			if !ok {
				// Канал закрылся! Делаем его nil, чтобы
				// select больше никогда не заходил в этот case.
				ch1 = nil
				fmt.Println("ch1 отключен")
				continue
			}
			fmt.Println("Получено из ch1:", v)

		case v, ok := <-ch2:
			if !ok {
				ch2 = nil // Отключаем ветку ch2
				fmt.Println("ch2 отключен")
				continue
			}
			fmt.Println("Получено из ch2:", v)
		}
	}
}
```
